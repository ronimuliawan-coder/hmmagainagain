# Taste learnings
- Prefers gated, high-assurance execution: verify state from primary sources (git, tracker, evidence log) before acting, present measured evidence (not claims), and stop for explicit owner approval at decision boundaries (resume choices, gate reviews, commit/push/PR vs. merge). Confidence: 0.7
- Communication: answers multi-decision prompts with terse numbered replies ("1. approved. 2. yes. 3. add."). Present decision requests as a short numbered list with a recommended option so they can be answered by number. Confidence: 0.6
- Trusts well-evidenced recommendations: approved the recommended resume option and assistant recommendations (track bun.lock, add per-unit plan docs) unmodified when the supporting case was measured/verified. Confidence: 0.6
- Keeps bookkeeping out of standalone commits: governance/tracker state flips (e.g., a unit's row → Done) ride with the next unit's PR rather than a churn commit (executed as such in the U4 changeset). Confidence: 0.7
- Isolates third-party/beta UI libraries behind a single wrapper-seam module — the only file allowed to import them — pinned to an exact version and re-verified against the registry at install (file-tree-wrapper → @pierre/trees; diff-view-wrapper → @pierre/diffs). Confidence: 0.7
- Performance work is measure-first: quantify the dominant risk end to end with stage-level timings against a committed deterministic fixture, record numbers in the tracker, and optimize only if a measured stage misses the budget — the verdict is stated as measured fact, not aspiration (executed in U4: 1M-line fixture measured per stage, scroll verdict from sampled frame gaps). Confidence: 0.8
- Prefers RED-first contract tests for new modules: failing tests are written and the RED run captured as before-state proof, then the implementation turns them green (U4: patch-to-items tests written and run RED before the module existed, per the owner-approved plan). Confidence: 0.6
- Git hygiene and commit format: stages with explicit paths so agent-harness state is never committed; commit subjects are conventional (`feat:`/`fix:`) and carry the unit/issue ID (e.g. `(RON-297)`), bodies are detailed bullets of what/why, and agent-authored commits include the `Co-authored-by: CommandCodeBot <noreply@commandcode.ai>` trailer. Confidence: 0.6
- PR + tracker lifecycle: on authorization, push the unit branch and open the PR into `dev` via `gh pr create`; the PR body is structured (Outcome / Validation / Notes) and links the Linear issue, the approved plan-of-record, and the measured-evidence table; merges are merge-commit-only. On PR open, comment the PR link + exact head SHA + gate-at-head status on the Linear issue and flip it to In Review. Confidence: 0.7
- Post-merge unit closeout ritual: when the owner reports a merge, verify it from primary sources before closing anything (`gh pr view` state + mergeCommit SHA, then fast-forward local `dev` to match), flip the Linear issue to Done, and append a structured COMPLETE entry to the append-only Evidence Log (Linear document) with fixed sections: done condition as a commit → PR → merge SHA chain, validation evidence, findings/deviations closed, watch-items, rollback impact, and the next unit explicitly marked not started — then report closure and stop before the next unit, which begins with a plan-of-record for approval. Confidence: 0.7
- Unit-start ritual: recon before planning — read the unit's Linear issue contract, grep the PRD for the unit's MUSTs/flow constraints, and read the installed dependency's type definitions (node_modules) to pin API shapes; then flip the issue to In Progress and post a structured START comment (unit contract, recon findings, planned shape, invariant notes, rollback impact) before drafting the plan. Confidence: 0.6
- Plan-of-record documents follow a fixed section template: draft-status line, Outcome, Safety model, Design, Dominant risk, Steps, Validation, Tracker points, Rollback impact, Done condition — summarized to the owner for confirmation before any implementation, with the doc itself riding in the unit's PR. Confidence: 0.7
- For units that mutate user data, planning is built around a safety model as the centerpiece: every write is an explicit user action, mutations are confined to recoverable state (e.g., index-only ops reversible via `git reset`), failures surface verbatim and are never bypassed or forced (hooks always run), smoke/self-tests only ever target throwaway fixtures (dedicated env-flag flows), and destructive operations are explicitly declared out of scope. Confidence: 0.7
